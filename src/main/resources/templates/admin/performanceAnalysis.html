1. LAZY (default)
N+1 PROBLEM

Hibernate carica le collection solo al primo accesso. Con N tornei genera 1 query per i tornei + 1 query per le squadre di ciascun torneo → problema N+1 query. Problema: se ci sono 10 tornei, vengono eseguite 11 query totali.

2. JOIN FETCH (JPQL custom)
OTTIMALE

Una singola query JPQL con LEFT JOIN FETCH carica Tornei e Squadre in un unico round-trip al database. DISTINCT previene i duplicati causati dalla relazione ManyToMany. Soluzione ottimale per leggibilità e prestazioni.

Query SQL generata:

SELECT DISTINCT t FROM Torneo t LEFT JOIN FETCH t.squadre
-- tradotto da Hibernate in:
SELECT DISTINCT t.*, s.* FROM torneo t
LEFT JOIN iscrizione_squadra_torneo ist ON t.id = ist.torneo_id
LEFT JOIN squadra s ON ist.squadra_id = s.id;
3. EntityGraph (@EntityGraph annotation)
OTTIMALE

L'annotazione @EntityGraph(attributePaths = {"squadre"}) sul metodo del repository istruisce Hibernate a caricare le squadre con un LEFT OUTER JOIN. Approccio dichiarativo: nessuna query JPQL manuale. Genera lo stesso numero di query della strategia JOIN FETCH (1 sola), con maggiore separazione delle responsabilità.

Conclusioni

Nel progetto è stata adottata la strategia EntityGraph. Come dimostrato dai benchmark, questa scelta riduce il numero di query da N+1 a 1 singola query, abbattendo il carico sul database e migliorando significativamente i tempi di risposta.
